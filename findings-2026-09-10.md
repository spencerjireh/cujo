# Findings from the 2026-09-10 review outage

What follows is what an investigation into "reviews stopped producing evidence"
turned up. One cause was found and fixed in provider configuration. Five further
problems were observed along the way. All five need a code change and none of
them were introduced by the outage, so they are recorded here rather than acted
on.

Evidence comes from the public run records at `cujo.spencerjireh.com`, from the
OpenRouter management API, and from the source in this repository.

Runs referenced throughout.

| run | pull request | date | outcome |
| --- | --- | --- | --- |
| `0c644064` | orders-api #36 | 2026-09-10 11:50 | three sub-agents 429 in under 1.6 s |
| `b30239c8` | orders-api #36 | 2026-09-10 12:12 | advisory posted, no check ran |
| `319e3f8a` | orders-api #37 | 2026-09-10 14:34 | all three checks ran, review posted |
| `b5724912` | orders-api #36 | 2026-09-10 23:37 | turn timeout, no review posted |

## Fixed — the guardrail narrowed the model to one endpoint

**Status.** Resolved on 2026-09-10 by configuration. No code change.

The OpenRouter workspace carried a guardrail named `cujo-allowlist` with
`enforce_zdr_openai = true`. Zero-data-retention enforcement strips a vendor's
own direct endpoints. For `openai/gpt-5.6-luna` that cut seven published
endpoints down to a single compliant Azure row, and that one row saturated.

Measured at the fan-out the rubric actually uses, three concurrent requests,
ten waves.

| model | requests failed | waves degraded | providers serving |
| --- | --- | --- | --- |
| `openai/gpt-5.6-luna`, ZDR on | 23 of 30 | 10 of 10 | Azure only |
| `z-ai/glm-5.3-flash`, ZDR on | 0 of 30 | 0 of 10 | Parasail, Together |
| `openai/gpt-5.6-luna`, ZDR off, BYOK | 0 of 30 | 0 of 10 | OpenAI direct |

The same guardrail also made a bring-your-own-key integration inert. BYOK routes
to the vendor's direct endpoint, which is exactly what ZDR enforcement removes,
so a correctly saved key returned `is_byok: false` on every request.

`enforce_zdr_openai` is now `false`. The other four vendor flags are unchanged.
Inference bills to the OpenAI account rather than to OpenRouter credits.

**Why this took a while to see.** A single hand-run request succeeded throughout,
because the limit is on concurrent requests and not on the key. Key health looked
fine at every level that gets checked first, with credits remaining, a daily cap
almost untouched, and `is_free_tier` false.

## Open problems

### 1. A rate-limited sub-agent is never retried

**Where.** `apps/cujo/src/clients/trueforge.ts:133`

The only backoff in the client is `bootstrapUntilReady`. A model error inside a
turn is terminal for that sub-agent. In run `0c644064` all three checks died
between 1425 ms and 1600 ms and nothing tried again.

The rubric spawns `tests`, `probes` and `smoke` in one message
(`agent/SKILL.md:176`), so a provider that throttles concurrency takes all three
at once rather than one. The design that makes reviews fast is the same one that
makes them fail together.

**Impact.** A transient provider fault becomes a permanently degraded review.

---

### 2. A run that executed nothing is recorded as `clean`

**Where.** `apps/cujo/src/review/fold.ts:466`

`status = "clean"` is reached whenever a review posted and no contradiction was
detected. Coverage is not part of that decision.

Run `b30239c8` ran zero checks, posted an advisory carrying four warnings, and
sits on the public board as `clean`. The review body is honest about what did
not happen. The status beside it is not, for anyone scanning a list.

**Impact.** The board cannot distinguish "ran everything and found nothing" from
"could not run anything". Those are opposite claims.

---

### 3. A timed-out turn posts no review at all

**Where.** `apps/cujo/src/review/runner.service.ts:414`

Run `b5724912` reached the 30-minute `CUJO_TURN_TIMEOUT_MS` ceiling with `smoke`
still running. `tests` had finished at 930,958 ms and `probes` at 1,215,088 ms,
both with real reports. Neither reached the pull request.

```
error    turn timeout: no terminal event
review   NONE
```

The same signature appears in `c7bf0e13` on 2026-08-30 and `ced0c934` on
2026-08-27, both `status=error` with `smoke` stuck in `running`. This predates
the outage.

**Impact.** Two completed checks are discarded because a third hung, and the
author sees nothing whatsoever. Silence is the one outcome that carries no
information.

---

### 4. The install step never reaches the service directory

**Where.** rubric setup, against a polyglot repository layout

`orders-api` holds six services under `services/`, and the repository root has no
manifest. Two runs recorded the consequence.

From `b30239c8`.

> The first wrapped install ran from `/work/head` and `/work/base` and exited 1
> because neither root contained a Python project.

From `319e3f8a`, which otherwise succeeded.

> `python -m pytest -q` exited 1 on base and head with
> `/usr/local/bin/python: No module named pytest`; no test IDs were collected.

**Impact.** The `tests` check is the strongest evidence available and it is lost
on every run against this repository. Probes and smoke compensate by exercising
the code directly, which is why `319e3f8a` still produced a useful review, but
the suite itself has never run.

---

### 5. The smoke sub-agent emits a report that fails schema validation

**Where.** hard rule `report_invalid`, observed in `319e3f8a`

```
runs.0.schema_version: Required (+31 more)
the hard rules still read this report, so what they found is unaffected
```

Two further details are worth separating. The envelope is short more than one
field, since the validator reports thirty-two. And this warning appears in the
run record and on the evidence page but not in the posted comment body, which
shows `0 critical, 1 warn` while the run holds two.

Whether the second part is intended is not established here. A malformed
envelope is arguably an operator concern rather than something to tell a pull
request author. `review/fold.ts` was not read closely enough to say which.

## Observation without a recommendation

A session is keyed by repository and pull request number
(`apps/cujo/src/store/runs.ts:131`). There is no way to give an existing pull
request a fresh session. Once a session accumulates failed turns there is no
reset short of opening a new pull request.

Run `b5724912` reused a session already holding four turns and its checks ran
30 to 60 times slower than the same checks on a fresh session in `319e3f8a`,
17,057 ms against 930,958 ms for `tests`. Session weight is the obvious suspect,
against a `CUJO_COMPACTION_THRESHOLD_TOKENS` of 200,000, but the diffs also
differ in size and nothing here isolates the two. This is a hypothesis and not a
finding.

The clean experiment is to open a new pull request carrying the identical diff.
A new number means a new session, so a fast run indicts the session and a slow
one indicts the diff.

## Re-verifying any of this

Guardrail state, which is undocumented and read-only through the browser
otherwise.

```bash
curl -s https://openrouter.ai/api/v1/guardrails \
  -H "Authorization: Bearer $OPENROUTER_MANAGEMENT_API_KEY"
```

Whether a model survives routing, and why it does not.

```bash
curl -s https://openrouter.ai/api/v1/models/openai/gpt-5.6-luna/endpoints \
  -H "Authorization: Bearer $OPENROUTER_API_KEY"
```

Adding `"provider": {"only": ["openai"], "allow_fallbacks": false}` to a
completion request returns a `routing_funnel` and named ineligibility reasons,
which is the fastest way to see a guardrail acting.

The model a run used is published on the run record itself, which is the only
place it is readable. Coolify returns environment keys without values.
